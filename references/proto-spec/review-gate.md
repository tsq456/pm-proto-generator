# 本批页面 Spec 确认门闩

## 适用范围

新建业务页面，以及改变既有页面职责、权限、关键字段、业务规则或状态流的增量修改，须先完成人工确认，再实现受影响的业务 HTML / Mock 行为。只写 Spec 可以交付草稿；从既有 HTML 补说明不倒逼重画页面。文案、间距等不改变业务语义的小改，以及修复原型以符合已确认 Spec，可直接执行。

用户明确要求跳过评审或已明确授权某项具体变更时，遵循用户指示，记录授权范围；不要重复索取相同确认。笼统的“生成原型”不等于确认尚未展示的 Spec。截图、竞品图、口述「做个类似的」同样不是确认：须先按 [模糊需求澄清](../../skills/proto-spec-generator/references/fuzzy-clarify.md) 同意结构草稿，再写入 Spec；未同意不得实现业务页。

## 准备可评审材料

先完成材料，再请求一次本批实现确认；不要只给计划就要求批准。向用户呈现时使用 [统一确认稿格式](../../skills/proto-spec-generator/references/confirmation-format.md) 的“本批 Spec 评审”格式；该格式不替代下列完整材料与确认记录。

- **站点地图与页面清单**：page-id、页面职责、入口/出口、跨页关系、本批范围；确认前的“页面”指清单和结构说明，不是已生成的业务 HTML。
- **本批各页 Spec**：布局分区、字段、按钮与宿主弹窗、权限、关键操作的条件/成功/失败/跨页影响，以及验收示例。
- **问题与假设**：会改变本批页面结构或核心行为的问题标为阻塞，先解决；不影响这些内容的问题写明非阻塞、采用的假设及影响范围，纳入本批评审。

可以先合并评审角色×场景、页面范围与 sitemap 草案；范围已明确则继续准备本批 Spec。只有范围歧义会导致大批返工时才单独提前确认。输入模糊时，提前确认的是 fuzzy-clarify 的需求理解稿（功能定位、结构与关键字典合并一轮，最多八问），不是逐字段口头审问。正式硬门闩在本批业务页面实现之前。澄清稿不是实现授权。

## 按批确认与记录

优先选一条完整核心流程涉及的页面，不强制整站一次确认，也不强制逐页问一次。其余页可保持 draft；跨批依赖须在 Spec 中明确本批可演示边界，未实现入口灰显。

在包内 `docs/spec-review.md` 记录每次确认：

| 批次 | page-id 与 Spec 版本 | sitemap 范围/版本 | 结论 | 确认依据 | 遗留问题/假设 |
| --- | --- | --- | --- | --- | --- |
| 本批编号 | 每个页面及其版本 | 所用地图版本或明确范围 | 待确认 / 已确认 / 需重审 | 用户实际确认的日期与原话摘要或可追溯引用 | 阻塞项应已解决；列非阻塞假设 |

初稿使用 draft，送审可设 reviewing；只有收到与当前材料相符的人工确认或已有明确授权，才记录依据并设 confirmed。禁止伪造确认、以 AI 自改状态代替人工批准，或把沉默当作同意。已有可靠确认记录直接复用，不要求用户为补记录再次确认。

实现前核对：本批每页 Spec 内容与记录的版本相符，sitemap 范围一致，阻塞项已解决。仅 sitemap confirmed、文件存在、页面非 planned、或少量页面抽检通过，都不代表其他页面获得实现授权。

## 变更与验收

- 新增页面或改变职责、权限、关键字段、规则、状态流时，先更新受影响 Spec 为待评审版本，在记录中标需重审并列影响页；用户本轮明确授权的具体变更可作为确认依据，其余新增决策待确认。未受影响页面可继续实现。
- 排版、无业务语义变化的文案修正、原型覆盖回填不触发重审；维护正常变更记录即可。
- 实现中发现需要新增业务决策，先回到 Spec，不能在 HTML 中自行补规则。现有原型不符合已确认 Spec 时直接修复原型。
- 实现完成后按已确认 Spec 验证字段、权限、状态变化和至少一条核心跨页路径，回填实际原型覆盖；不得把尚未实现的内容标为已演示。
