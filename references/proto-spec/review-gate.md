# 接收与实现放行规则

## 判断实现依据

上游原稿和实际确认/授权是业务依据；逐页 Spec 是派生材料，不再提交一次独立产品审批。源文档、章节、版本或快照以及确认依据记录在包内 `docs/spec-intake.md`。旧 `docs/spec-review.md` 可直接引用。

核对三项：

1. 本批范围、角色、页面行为、固定场景与验收足以实现；所需依赖能读取。
2. 来源确认与当前版本相符；没有影响本批的未解决冲突或“需检查”变更。
3. 派生说明、sitemap 和本地映射未改变产品语义，完整路径的依赖已经就绪。

满足后可记录“就绪”并按已有实现请求继续，不再询问格式转换是否获批。`confirmed` 字样、文件存在或最近编辑时间本身不是确认依据。用户实际授权优先，准确记录其范围；不能伪造记录或把沉默作为确认。

## 部分就绪

只暂停受缺口影响的页面及依赖链；不依赖缺口且能闭环的批次可以继续。全局导航等共享决策未定时，依赖它的页面不能自行选方案。无关的预算或外部系统未决项不自动阻断静态原型。

可写带来源和阻塞说明的 draft，但不能将冲突合并成确定规则。草稿不生成业务 HTML/运行 Mock；未实现入口不链接到不存在页面。

## 问题分流

技术路径、字段键、英文枚举、内部 ID 缺失：实现适配，自行命名并记录。
业务范围、状态、权限、对象关系、操作结果冲突：集中反馈来源原文、影响页面和上游责任层。已确认 Spec 与 kit 默认表现不同不算业务未决；按 Spec 实现。技术栈不兼容或能力无法覆盖时报告具体差异，不静默换栈或用占位冒充实现。

## 变更与验收

业务变更通过新版上游输入；已有具体授权与来源一致时复用。单纯样式调整和修复实现偏差可直接执行，不倒逼改上游。上游变更后重新核对受影响范围，不重审整站。

实现后回填“已演示/部分演示/未演示”，列出测试结果及偏差。原型未实现不等于产品未确认；不得为通过验收改写产品要求。
