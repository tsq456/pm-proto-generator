# 模糊需求澄清（写 Spec 之前）

> 截图、竞品图、口述「做个类似的」只是参考，不是方案，也不是确认。先交功能定位、结构草稿和关键业务字典，一轮问完影响方向、骨架或关键业务含义的未决点，人改完或明确同意后，再写入 Spec。此步不写业务 HTML。

不另建子技能。本文件是 `proto-spec-generator` 在 Phase 2.5 之前的强制前置；主技能未走完不得画本批业务页。

## 何时必须走

输入属于下面任一种，且下方「结构项」尚未经人确认：

- 截图、竞品图，或「按这个做 / 做个类似的」
- 只有目标或场景，没有主路径、页面身份、页型、字段落点、对象边界、状态下的操作、本批不做

**不走：**

- 已有与本轮相符的 confirmed Spec，或用户本轮明确授权的某一项具体变更
- 不改变业务语义的文案、间距、列顺序
- 按已确认 Spec 修复原型

贴图、笼统说「生成原型 / 做吧」、沉默，都不算确认。已确认材料直接复用，不重复问。

## 做法（一轮，禁止逐条问）

1. 用户已经说的话、贴的图就是模糊输入。不要要求把同一段需求重写一遍。只有完全没有业务内容时，才先要一段原话，然后停止。
2. 先读 [confirmation-format.md](./confirmation-format.md)，按统一格式先给基于理解的功能定位，再给下面的结构草稿与关键业务字典；明确用户、场景、核心问题、预期结果和职责边界。依据标签按该参考区分用户明确、沿用已确认、从图推断、AI 建议和信息缺失。此步不写 `proto-spec/`、不写业务 HTML、不改 `sitemap.yaml`。
3. 只把会改变功能定位、范围、页面骨架或关键业务含义，且草稿里仍空白或互相冲突的点收成**一批**问题。一次问完，最多 6～8 个，不要凑满。通常包含：主路径、页面与入口、页型与表单载体、字段落点、状态与本批不做。方向已足够明确、主路径仍空白或与页面清单对不上时，必须占一个问题名额。
4. 不影响定位、范围、骨架或关键业务含义的写成非阻塞假设，不单独问。定位、结构、字典默认同轮确认，不按章节逐次确认。若定位分岔导致结构无法合理推导，先确认方向，不编造后续细节。禁止逐项来回确认，禁止每个 Phase 都停一次。
5. 人改完草稿，或明确同意当前这份草稿之后，再写入 Spec。未关闭的问题不得写进 Spec 正文冒充已定规则；若仍阻塞，放「待确认事项」并标阻塞，不能据此实现页面。

## 草稿必须含这些结构项

| 项 | 写什么 |
| --- | --- |
| 主路径 | 一条主流程，5～8 步。每步写：谁触发、系统判断什么、状态变成什么、落在哪一页。驳回、作废等支路只有会多出页面或改变状态机时才写；否则不展开 |
| 页面身份与入口 | 新页还是改已有页；拟定 `page-id`（`{entity}-{pageType}`）；菜单挂载；与主路径里的页面一致 |
| 页型与表单载体 | 列表 / 详情 / 整页表单 / 抽屉 / 仅确认用弹窗。载体按仓库 `references/form-carrier.md`，不要按字段多少把表单送进弹窗 |
| 字段落点 | 按用途拆开：筛选、列表列、创建/编辑、详情只读、关联子表。不要只给一张字段总表 |
| 对象边界 | 主对象是什么；父子、一对多是主表字段，还是子表 / Tab / 另一页 |
| 状态下的操作 | 有哪些状态；各状态下工具栏和行内操作显隐；危险操作是否单独确认。须能对上主路径里的状态变化 |
| 本批不做 | 图里有、但本批不做的导出、批量、统计、审批等 |

完整结构草稿中主路径是必填，不能放进「本轮不问」；仅先确认定位分岔时可暂缓结构草稿。它决定有哪些页、状态在哪一步变。只有入口出口、或只列某状态下的按钮，不算写了主路径。

以下内容先写当前理解或建议；仅当存在未决或冲突且会影响结构或关键业务含义时，才纳入待决问题：

- 谁能看、数据按什么切（本园区 / 本部门 / 全部）
- 关键业务字典：分类、等级等候选值及含义、用途、来源与待决点必须随草稿呈现；无适用项则说明无。流程状态引用上面的状态与操作；关联业务数据说明来源与选择范围。单选/多选、默认项、级联、停用历史值处理按影响补充，具体表头与边界见 confirmation-format

**不要写进草稿：** 交互长文、每种失败提示、按钮文案、空态用词、间距与列宽、验收清单、模拟数据里的具体名字。这些留到确认后的 Spec，或实现时再定。主路径的短步骤不算交互长文。

## 确认稿怎么写

统一使用 [confirmation-format.md](./confirmation-format.md) 的模板与回复方式，不自行重排成只有问题的问卷。Q 编号在同批往返中保持稳定；每题给当前建议及理由、真实备选差异和影响。无阻塞问题时省略问题表，允许整体确认草稿。目录、kits 等技术检查不作为业务问题。

## 确认后写到哪

- 功能定位、范围、场景、首批页、已确认的主路径与跨页共用字典：并入 [req-breakdown.md](./req-breakdown.md)；确认稿可落包内 `docs/req-breakdown.md`，也可只留在对话记录
- 各页字段、单页字典、规则、状态、权限，以及主路径在该页上的步骤：写入 `proto-spec/<page-id>.md`（未进入本批实现确认前 `status` 保持 `draft`）
- 不另建第二份规格文件。澄清稿不是实现授权
- 业务 HTML 仍须等本批 Spec 按仓库 [确认规则](../../../references/proto-spec/review-gate.md) 人工确认

增量需求只澄清**本轮新增或变更**的结构项，不重问已确认页面。
