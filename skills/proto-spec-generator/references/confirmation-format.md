# 面向用户的确认稿格式

本文件约束确认材料的呈现方式。输出需求澄清、范围变更或本批 Spec 评审材料前必读。是否需要确认、何时可以实现，仍按 fuzzy-clarify 和仓库 review-gate；本文件不增加确认轮次。用户指定格式时优先遵循用户要求。

## 共同规则

- 先给基于需求理解的建议，再集中列需要用户裁决的问题；不能只交问卷。
- 开头写清本轮确认对象、版本、范围及确认后的下一步。需求澄清与实现前 Spec 评审使用不同标题，不用笼统的“方案确认”。
- 区分内容依据：`【用户明确】`、`【沿用已确认】`、`【从图推断】`、`【AI 建议】`、`【信息缺失】`。引用既有材料时给名称/位置；前两者才表示已有依据，推断和建议不等于已确认。
- 章节顺序、问题编号、表头保持一致。正文用短段落；并列内容用表；流程用编号列表。表格最多六列，单元格不塞整段流程或多层列表。
- 同一问题只在“待决问题”出现一次，其他位置引用 Q 编号。每个问题只有一个决策；独立决策拆开编号。Q1、Q2 等在同批往返中保持稳定，新问题追加编号，不挪用已关闭编号。
- 问题仅收集未决且影响定位、范围、页面结构或关键业务含义的点，一轮最多八个，不凑数。表内的字典候选值不逐项变成提问。
- 无关键字典时写“本批无新增或变更的关键业务字典”；无待决问题时写“无阻塞问题，可整体确认当前草稿”，省略空表。交付前删除模板占位文字。
- 已有确认直接引用。增量只展示变化与影响；不为套模板重问背景、字典或已确认规则。局部一项变更可压缩为“本轮范围/建议与依据/影响/待决问题/回复方式”，无需铺开完整模板。

## 模糊需求确认稿：固定顺序

以下是结构模板，不是预置业务答案。结构项的具体要求见 [fuzzy-clarify.md](./fuzzy-clarify.md)。

确认后：据此准备 sitemap 与 Spec 草稿；本次不代表业务页面实现确认。

### 功能定位与字典的内容边界

- 功能定位应在页面细节之前。若存在两种会导致完全不同方案的定位，先提供推荐方向、依据及简短备选，将方向作为待决问题；本轮可省略尚无法合理推导的结构和字典，不强行编造。通常定位、结构、字典合并一轮确认。
- 字典只列本批关键分类、等级、原因等，写明候选值含义，尤其是影响流程、权限、统计或核心录入的值。未知值写信息缺失，不为填表虚构行业标准。
- 流程状态与“状态与操作”共用同一组定义；字典表可引用该节，不重复创造一套状态。部门、人员、设备等是关联业务数据，应说明来源和可选范围，不列成固定枚举。
- 单选/多选、默认项、级联、停用历史值处理，仅在影响本批方案时补充。候选值过长时按 D 编号在表后分段，避免宽表。
- 确认后功能定位并入需求拆清/PRD；跨页共用字典可统一放在包内 `docs/req-breakdown.md`，相关 Spec 引用该定义；仅单页使用的字典写入该页 Spec。不另建并行规格，不让不同页面各自发明字典值。

## 本批 Spec 评审：沿用格式，替换内容

标题使用“<功能名称> · 本批 Spec 实现确认稿 · <版本>”。依次给出：

1. **本轮范围与变更**：批次、页面、职责、相对已确认稿的变化；没有变化的定位和字典只引用。
2. **评审材料**：用“材料 / 范围与版本 / 可打开链接”三列表，列 sitemap、页面清单、本批每页完整 Spec。摘要不能替代完整材料。
3. **待决问题与假设**：沿用 Q 编号、表头和依据标签；阻塞项未解决不得声称可实现。
4. **回复方式与下一步**：写明此次确认的是哪些版本、哪些页面的实现。示例：“同意按上述版本实现本批页面”；只确认某几页时仅记录其授权范围。

提出修改后先更新对应材料，确认依据须与最终范围和版本一致。明确具体授权可直接复用；澄清稿的同意不能被改记为完整 Spec 的实现确认。
